# 委派方式 × 查资料深度：12 格消耗矩阵（2026-09-21）

## 1. 这次要量什么

本仓的调用协议要求「先查后想、先索引后精确条目」，并把**层数上限**定为 2
（`docs/roadmap/LOOKUP_DEPTH_RESEARCH.md` §5）。那条分析量的是**一次会话内部**
每一步查资料的价格。本页量的是它的上游问题：

1. **把活派出去时，派给谁**——`subagent`（一个子 agent）、`agent_teams`（建队 + 成员）、
   `workflow`（编排里的一次 `agent()` 调用）三者，同一个活各花多少；
2. **让被派的一方查多深**——`inline`（规格直接进提示词，0 跳）、`one-hop`（点名唯一权威文件，
   1 跳）、`two-hop`（只给目录，要求自己判定哪份当前有效，2 跳）、`dump`（规格埋在
   一份 ~195 kB 拼接大文件里）。

结论用于 `docs/usage/MCP_CONSUMER.md` 的「Delegation and lookup depth (measured)」一节：
**该协议的"候选索引优先"是对的方向，而层数不仅该有上限，入口还应该由派活的人直接指定。**
本页是那条建议的证据，不是建议本身。

## 2. 方法与隔离

- **固定活**：按一份自撰规格实现一个小模块，验收 = **6 个可见用例 + 15 个隐藏用例**
  （隐藏集被派的一方看不到），覆盖规范化合并、最少 CIDR 分解、边界前缀、非法输入的错误
  消息、幂等与千项规模。参考答案先自测 15/15 通过才允许开跑。
- **每格只有一个信息来源**：12 个运行目录各自只放一种来源；提示词除"规格从哪来"一行外
  逐字相同；12 份可见测试与 12 份 README 的 md5 各自唯一。
- **串行**执行，一组跑完再起下一组；读数取子会话日志里的网关 `usage`，
  按 `parentSession` + 该组 `[start, end+5s]` 时间窗归属，不靠 label 猜。
- **加权口径**与已公开报告 02 相同：输出 1 · 未命中输入 0.25 · 缓存读 0.025。
- **作废重跑**：首轮 4 组数据丢弃。原因是运行目录落在带治理钩子的工作区里，子会话被自动
  触发的 `apg context` 污染，多出工具调用与未命中输入；重建在治理范围之外的独立目录后重跑。
- **`fork` 委派排除**：fork 子会话是**记忆延续**（继承父会话状态），不是"把活派出去"，
  消耗结构与其余三种不可比。

## 5. 取证：每一格实际读了什么

`json` 的 `sourcesRead` 只保留**在该运行目录里真实存在**的路径（从工具参数里抽取，
再逐个 `exists()` 过滤，避免把报告正文里顺口提到的路径算成一次读取）。摘要：

| 运行 | 读到的来源 |
|---|---|
| spawn-inline / teams-inline / flow-inline | 只有 `README.md` + `test_netrange.py`（规格在提示词里） |
| spawn-one-hop / teams-one-hop / flow-one-hop | 上述 + `docs/07-spec-netrange.md`（唯一权威那份） |
| spawn-two-hop | 上述 + `INDEX.md` + **也读了已被取代的 `docs/03-notes-legacy.md`** |
| teams-two-hop | 上述 + `INDEX.md`（未读 legacy） |
| flow-two-hop | 上述 + `INDEX.md` + `docs/00-notes.md` + `docs/03-notes-legacy.md` |
| *-dump（三格） | `ALL-NOTES.txt` + 可见材料；**三格都没有整体读入**，都先 `wc -l`/`grep -n` 定位、再按窗口读 |

委派方式的差别也直接看得见：每个 `agent_teams` 格子都多出 `agent_teams_claim_task`、
`agent_teams_update_task`×2、`agent_teams_send_message`、`report` 这些**队务回合**
（有的还多一次 `agent_teams_status`），而找资料的行为与对应的单子 agent 格一致。

## 6. 结论

1. **成本由轮数决定，不由上下文体积决定**：`corr = 0.924`；最便宜两格都是 6 个请求
   （17.1k / 16.2k），最贵两格都是 18 个请求（41.9k / 43.6k）。709.5k 缓存读按 0.025 只值
   17.7k 加权，而多出来的十几轮输出本身就更贵。
2. **入口由派活的人指定，比让被派的人自己判定更省**：`one-hop` 均值最低（26.8k），
   `two-hop` 稳定最贵（37.0k）。"哪一份当前有效"这个判断只能用轮数买。
3. **大文件本身不是主要成本，"不知道看哪里"才是**：`dump` 三格都先定位再窗口读，
   均值 34.0k，低于 `two-hop`。若换成一次性整体读入，这一格会明显更贵——本轮没有观测到该路径。
4. **为一件活建队，贵在队务不在查资料**：`agent_teams` 平均 +44%，差额几乎全在未命中输入
   （31.2–39.4k，对比 `subagent` 的 3.6–12.7k），即第一轮的队伍/任务引导上下文（不入缓存）。
   但它**最稳**（极差 1.32×，其余 2.05×/2.69×）：要平均便宜选单子 agent，要让最坏情况
   可预测才建队。

## 7. 这不主张什么

- **每格 n=1**。组内极差（最大 2.69×）大于部分格间差值，且在一处出现方向翻转
  （`subagent` 组里 `one-hop` 比 `two-hop` 贵，`workflow` 组里相反）。**排序是方向性的，
  不是统计显著的**；要下结论需每格 ≥3 次重复。
- **12 格全部一次通过**（隐藏 15/15），因此本矩阵只排"成本"，**不排"成功率"**。
  也不证明"三种委派一样好"——只是这个任务的难度不足以让成功率产生区分。
- **单模型路由、单任务**。绝对数字随模型、定价与任务规模变化，趋势比绝对值可靠。
- **墙钟含编排开销**，不主张"便宜就更快或更慢"。
- 本仓的 `docs/roadmap/LOOKUP_DEPTH_RESEARCH.md` §1–§4 用的是**本仓文档语料的 token 估算**；
  本页用的是**网关 usage 的加权单位**。两套刻度不可直接相加或换算。
